# AI WORKFLOW — telecom-news

Постоянная инструкция для LLM, работающей над проектом. Три обязательных протокола: Startup, Work, End-of-session.

---

## 1. Startup protocol (начало нового чата)

Startup двухуровневый: сначала дешёвый Level 1; подробные документы и код читаются лениво (Level 2) только когда нужны для конкретной задачи.

### Level 1 — всегда (обязательно, по порядку)

#### 1.1 Определить рабочий каталог
```bash
pwd
```
Ожидается `/mnt/c/Working/Develop/AIProjects/telecom-news`. Если нет — сообщить пользователю и не продолжать.

#### 1.2 Прочитать только `docs/CURRENT.md`
Это короткий canonical working-state файл (стадия, milestone, следующий шаг, ключевые решения, фактическая реализация, blockers). **В Level 1 остальную документацию НЕ читать.**

#### 1.3 Проверить Git
```bash
git status --short
git log -3 --oneline
```
Актуальный HEAD — факт из Git, не из документации.

#### 1.4 Сверить CURRENT.md с реальностью
Проверить, что CURRENT.md соответствует фактическому Git-состоянию и дереву файлов (при необходимости `find . -not -path './.git/*'`). Выявить расхождения.

#### 1.5 Сообщить пользователю
В начале ответа сообщить:
- текущую стадию;
- текущий milestone;
- следующий конкретный шаг;
- blockers или очевидные несоответствия между CURRENT.md и реальностью.

### Level 2 — lazy context (только по необходимости)

После определения конкретной задачи читать **только необходимые** материалы:

| Документ | Когда читать |
|---|---|
| `docs/ROADMAP.md` | нужно уточнить scope или критерии milestone |
| `docs/ARCHITECTURE.md` | только разделы, относящиеся к изменяемому компоненту |
| `docs/DECISIONS.md` | задача затрагивает архитектурное решение |
| `docs/SESSION_HANDOFF.md` | CURRENT.md недостаточно или предыдущая сессия завершилась с незаконченной работой |
| `docs/PROJECT_STATE.md` | нужна подробная сверка состояния |
| `README.md` | задача меняет пользовательскую документацию |
| исходный код | только файлы, относящиеся к текущей задаче (перед изменением — обязательно прочитать) |

Правила Level 2:
- Не перечитывать один и тот же документ повторно в пределах одного чата без конкретной причины.
- Не читать «на всякий случай» документы, не относящиеся к задаче.

### 1.6 Не менять ничего до подтверждения
**Ничего не изменять** в файлах, коде или Git до явного подтверждения пользователя.

## 2. Work protocol (во время разработки)

Правила во время работы:

- Работать **небольшими завершёнными этапами**. Не реализовывать несколько milestones одновременно.
- Перед изменением существующего кода — **сначала прочитать** относящиеся к задаче файлы.
- После изменений — запускать **относящиеся к ним тесты**.
- **Не считать задачу выполненной**, если тесты падают.
- **Не придумывать** результаты команд или тестов — только фактический вывод.
- **Не изменять архитектуру** без отражения этого в `docs/DECISIONS.md` и (при необходимости) `README.md`.
- **Не создавать Git commit** без явного разрешения пользователя, если пользователь не дал другое правило.

---

## 3. End-of-session protocol (перед завершением чата)

Перед завершением рабочей сессии:

1. Выполнить существующие тесты, относящиеся к сделанным изменениям.
2. Выполнить `git status`.
3. **Обязательно актуализировать `docs/CURRENT.md`** — это главный короткий handoff для следующего чата (стадия, milestone, следующий шаг, ключевые решения, фактическая реализация, blockers). Не копировать в него полный ROADMAP/архитектуру/историю.
4. Обновить `docs/PROJECT_STATE.md` и `docs/SESSION_HANDOFF.md` **только если их содержимое действительно изменилось** (не дублировать одинаковое подробное описание состояния сразу в нескольких файлах).
5. При необходимости обновить `docs/DECISIONS.md` (новые решения), `docs/ROADMAP.md`, `docs/ARCHITECTURE.md`.
6. Показать пользователю **краткий итог** сессии.
7. Указать **следующий конкретный шаг**.

---

## Общие принципы

- Документация в `docs/` — источник истины для LLM между сессиями. Если файл противоречит реальности, реальность побеждает и документацию нужно исправить.
- Никогда не выдумывать состояние файлов, результатов команд или тестов.
- Сохранять проект в состоянии, из которого новый чат может восстановиться только по файлам и Git.
