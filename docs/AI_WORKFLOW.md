# AI WORKFLOW — telecom-news

Постоянная инструкция для LLM, работающей над проектом. Три обязательных протокола: Startup, Work, End-of-session.

---

## 1. Startup protocol (начало нового чата)

При начале работы модель **обязана** выполнить по порядку:

### 1.1 Определить рабочий каталог
```bash
pwd
```
Ожидается `/mnt/c/Working/Develop/AIProjects/telecom-news`. Если нет — сообщить пользователю и не продолжать.

### 1.2 Прочитать документацию
Обязательно прочитать:
- `README.md`
- `docs/PROJECT_STATE.md`
- `docs/DECISIONS.md`
- `docs/SESSION_HANDOFF.md`

Дополнительно, **если существуют**:
- `docs/ROADMAP.md`
- `docs/ARCHITECTURE.md`

### 1.3 Проверить Git
```bash
git status
git log --oneline -5
```

### 1.4 Сверить документацию с реальностью
Сравнить описанное в PROJECT_STATE.md с фактическим деревом файлов (`find . -not -path './.git/*'`). Выявить расхождения.

### 1.5 Сообщить пользователю
В начале ответа сообщить:
- текущее состояние проекта;
- текущий milestone / этап;
- следующий шаг (из PROJECT_STATE.md);
- найденные несоответствия между документацией и реальностью.

### 1.6 Не менять ничего до подтверждения
**Ничего не изменять** в файлах, коде или Git до явного подтверждения пользователя.

## 2. Work protocol (во время разработки)

Правила во время работы:

- Работать **небольшими завершёнными этапами**. Не реализовывать несколько milestones одновременно.
- Перед изменением существующего кода — **сначала прочитать** относящиеся к задаче файлы.
- После изменений — запускать **относящиеся к ним тесты**.
- **Не считать задачу выполненной**, если тесты падают.
- **Не придумывать** результаты команд или тестов — только фактический вывод.
- **Не изменять архитектуру** без отражения этого в `docs/DECISIONS.md` и (при необходимости) `README.md`.
- **Не создавать Git commit** без явного разрешения пользователя, если пользователь не дал другое правило.

---

## 3. End-of-session protocol (перед завершением чата)

Перед завершением рабочей сессии:

1. Выполнить существующие тесты, относящиеся к сделанным изменениям.
2. Выполнить `git status`.
3. Обновить `docs/PROJECT_STATE.md` (фактическое состояние, следующий шаг).
4. Обновить `docs/SESSION_HANDOFF.md` (что сделано, на чём остановились).
5. При необходимости обновить `docs/DECISIONS.md` (новые решения).
6. При необходимости обновить `docs/ROADMAP.md` и `docs/ARCHITECTURE.md`.
7. Показать пользователю **краткий итог** сессии.
8. Указать **следующий конкретный шаг**.

---

## Общие принципы

- Документация в `docs/` — источник истины для LLM между сессиями. Если файл противоречит реальности, реальность побеждает и документацию нужно исправить.
- Никогда не выдумывать состояние файлов, результатов команд или тестов.
- Сохранять проект в состоянии, из которого новый чат может восстановиться только по файлам и Git.
