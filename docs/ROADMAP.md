## M0 — Foundation

**Цель:** минимальный технический фундамент приложения (без реальных новостей, LLM и Telegram).

**Входит:**
- `pyproject.toml` (Python 3.10+, src-layout; **без внешних runtime-зависимостей** — только pytest как dev-зависимость; httpx/feedparser добавляются в M1, fastapi/uvicorn не входят в MVP — D-004)
- Python package `src/telecom_news/`: `__init__.py` (субпакеты `collectors`, `processors`, `llm`, `storage`, `delivery` создаются вместе с их содержимым в M1–M4; пустые каталоги без файлов не отслеживаются Git'ом)
- Удаление пустого каталога `src/telecom_news/api/` (не входит в MVP, D-004)
- `config.py`: пути, LM Studio endpoint, env-переменные (без реальных вызовов)
- Настройка стандартного Python logging
- Минимальная доменная модель `Article` (`src/telecom_news/models.py`) — только dataclass, без БД и persistence; storage-specific модели появятся в M2
- CLI skeleton: `python -m telecom_news --help`, заглушки команд `run/status`
- Тестовая инфраструктура (pytest) + минимальный smoke test

**Явно НЕ входит:** httpx; feedparser; реальный RSS/API collector; SQLite; LM Studio; Telegram; scheduler; scraping; FastAPI.

**Ожидаемые файлы:** `pyproject.toml`, `src/telecom_news/{__init__,main,config,logging_setup,models}.py`, `tests/test_smoke.py`.

**Зависимости:** завершение planning (это первый milestone).

**Критерии готовности:**
- `pip install -e .` работает в чистом venv;
- `python -m telecom_news --help` печатает список команд;
- `pytest` зелёный (smoke test: импорт пакета, модель Article создаётся, CLI help).

**Обязательные тесты:** smoke test импорта и модели.

**Проверка результата:** команды выше выполнены в чистом окружении.

**Условие перехода к M1:** все критерии выполнены, working tree закоммичен (по разрешению пользователя).

## M1 — One News Source

**Цель:** минимальный настоящий вертикальный сбор: одна реальная новость из SMS/messaging-экосистемы из одного источника → внутренняя модель `Article`.

**Входит:**
- Выбор **одного реального источника** (русскоязычного или англоязычного), регулярно публикующего материалы о SMS/messaging-рынке; фактическая проверка доступных вариантов: предпочтение — структурированный официальный интерфейс (RSS или API, D-007); scraping не используется, если RSS/API решает задачу
- Добавление зависимостей `httpx` и `feedparser` в `pyproject.toml` (первый milestone, где они становятся необходимыми)
- `collectors/base.py` (`RawItem`, таймауты, retry) и коллектор выбранного механизма (`collectors/rss.py` или `collectors/api.py`)
- `processors/normalize.py`: `RawItem → Article` (нормализация URL, текст, язык ru/en, `content_hash`)
- CLI: `python -m telecom_news collect --source <id>` печатает полученные статьи в человекочитаемом виде

**Явно НЕ входит:** SQLite; дедупликация; LLM; Telegram.

**Ожидаемые файлы:** `collectors/{base,rss}.py`, `processors/normalize.py`, обновление `config.py` (источник), `tests/test_collectors.py`, `tests/test_normalize.py`.

**Зависимости:** M0.

**Критерии готовности:**
- Запуск `collect` по реальному источнику возвращает ≥1 статью, относящуюся к SMS/messaging-тематике;
- Каждая статья корректно нормализована: URL без tracking-параметров, `published_at` в UTC, `content_hash` стабильный (повторный запуск даёт тот же hash);
- Тесты зелёные.

**Обязательные тесты:** парсинг RSS из фикстуры (без сети), нормализация URL/времени, стабильность `content_hash`.

**Проверка результата:** реальный запуск CLI по выбранному источнику + вывод.

**Условие перехода к M2:** критерии выполнены; источник зафиксирован в конфигурации и документации.

## M2 — Storage and Deduplication

**Цель:** персистентность статей и предотвращение повторной обработки.

**Входит:**
- Storage-specific модели/схема в `storage/` (доменная модель `Article` уже определена в M0 в `src/telecom_news/models.py`)
- SQLite (`storage/database.py`, stdlib `sqlite3`): схема, создание таблиц при старте, путь из конфигурации (`data/news.db`)
- Сохранение статей; стабильные идентификаторы (`content_hash`, нормализованный URL)
- Статусы обработки: `new → processed → published` (+ `skipped`, `error`)
- Дедупликация: повторный запуск не сохраняет и не обрабатывает уже известные статьи

**Явно НЕ входит:** LLM; Telegram; релевантность.

**Ожидаемые файлы:** `storage/database.py`, `processors/dedup.py`, CLI `collect` с сохранением в БД, `tests/test_storage.py`, `tests/test_dedup.py`.

**Зависимости:** M1.

**Критерии готовности:**
- Повторный запуск `collect` не создаёт дубликатов (по hash и URL);
- Счётчики по статусам видны через CLI (`status`);
- БД переживает перезапуск (данные сохраняются).

**Обязательные тесты:** upsert по hash, идемпотентность повторного сохранения, переходы статусов.

**Проверка результата:** два последовательных запуска `collect`; проверка содержимого БД.

**Условие перехода к M3:** критерии выполнены.

## M3 — LLM Processing

**Цель:** интеграция с локальной моделью через LM Studio и обработка статей.

**Входит:**
- `llm/client.py`: HTTP-клиент LM Studio (OpenAI-совместимый endpoint, по умолчанию `http://localhost:1234/v1`), таймауты, retry, `LLMUnavailableError`
- Проверка релевантности **SMS/messaging-тематике** (общие телеком-новости без связи с SMS → irrelevant)
- Классификация типа новости: technology / vendor / aggregator / carrier / product_service / partnership / ma_investment / security_antifraud / regulation
- Summarization; обработка RU и EN; перевод при необходимости (язык источника ≠ целевой язык канала)
- Структурированный результат (`llm_result` JSON); нерелевантные статьи → `skipped`
- Обработка ошибки/недоступности LM Studio: pipeline не падает, статья остаётся для повторной обработки

**Явно НЕ входит:** публикация в Telegram; scheduler.

**Ожидаемые файлы:** `llm/client.py`, `processors/relevance.py`, `processors/summarize.py`, CLI `process`, `tests/test_llm_client.py` (mock-сервер), `tests/test_relevance.py`.

**Зависимости:** M2; доступная локальная модель в LM Studio.

**Критерии готовности:**
- Релевантная SMS-статья получает `category` и саммари на целевом языке, статус `processed`;
- Нерелевантная (общая телеком) статья → `skipped`, без суммаризации;
- При недоступном LM Studio: явная ошибка в логе, статьи не теряются, повторный запуск обрабатывает их заново.

**Обязательные тесты:** клиент LLM против mock HTTP-сервера (успех, таймаут, 5xx); промпты/парсинг результата на фикстурах; поведение при недоступности.

**Проверка результата:** реальный прогон `process` с запущенным LM Studio по статьям из M2.

**Условие перехода к M4:** критерии выполнены.

## M4 — Telegram Publishing

**Цель:** публикация обработанных новостей в Telegram-канале через Bot API.

**Входит:**
- `delivery/telegram.py`: Telegram Bot API (`sendMessage`), токен/chat_id из env
- Формат публикации: заголовок, саммари, категория, ссылка, язык
- Preview/dry-run: вывод текста публикации без отправки
- Тестовая отправка в тестовый канал
- Статус `published`; защита от повторной публикации (публикуется только `processed`, перевод в `published` атомарен)

**Явно НЕ входит:** scheduler; аналитика канала.

**Ожидаемые файлы:** `delivery/telegram.py`, CLI `publish --dry-run`, `tests/test_telegram.py` (mock Bot API).

**Зависимости:** M3; токен бота и chat_id тестового канала.

**Критерии готовности:**
- `publish --dry-run` печатает корректный текст без отправки;
- Тестовая отправка доставляет сообщение в тестовый канал;
- Повторный запуск `publish` не дублирует уже опубликованные статьи.

**Обязательные тесты:** форматирование публикации, dry-run (без сети), идемпотентность публикации против mock API и БД.

**Проверка результата:** реальная тестовая отправка + повторный запуск без дублей.

**Условие перехода к M5:** критерии выполнены. **На этом моменте MVP-сценарий пройден вручную (см. MVP Definition).**

## M5 — Automation

**Цель:** автоматический ежедневный запуск pipeline.

**Входит:**
- Scheduler: периодический запуск `python -m telecom_news run` (встроенная петля или системный cron)
- Retries и обработка временных ошибок по этапам (см. ARCHITECTURE §3.14)
- Logging выполнения каждого прогона (`data/logs/`)
- Понятные exit codes (0 = успех; зафиксированный набор ненулевых кодов: сбой источников, сбой LLM, сбой публикации)

**Явно НЕ входит:** distributed workers, очереди.

**Ожидаемые файлы:** `scheduler.py`, обновление CLI (`run`), документация exit codes в README.

**Зависимости:** M4.

**Критерии готовности:**
- Pipeline запускается по расписанию без ручного вмешательства;
- Временная ошибка (сеть/LLM/Telegram) не роняет прогон и не дублирует публикации;
- Exit codes задокументированы и проверяются тестами.

**Обязательные тесты:** exit codes CLI; логирование прогона; retry-логика на mock-ошибках.

**Проверка результата:** несколько автоматических прогонов, включая симуляцию временного сбоя.

**Условие перехода к M6:** критерии выполнены.

## M6 — Multiple Sources

**Цель:** расширение набора реальных источников с изоляцией ошибок.

**Входит:**
- Дополнительные источники: RSS; API; scraping **только там, где нет надёжного интерфейса** (RSS/API)
- Приоритет источников: регулярные материалы о SMS/messaging-рынке, SMS-вендорах, агрегаторах, операторах/carriers и технологических изменениях экосистемы
- Конфигурация источников: включение/отключение (`enabled`)
- Source health: статус последнего успешного/неудачного сбора
- Ошибка одного источника не ломает весь pipeline

**Явно НЕ входит:** семантическая дедупликация; новые каналы доставки.

**Ожидаемые файлы:** новые `collectors/*.py`, расширение конфигурации, CLI `status` с health источников, тесты на фикстурах.

**Зависимости:** M5.

**Критерии готовности:**
- ≥3 активных источника (ru и en), включение/отключение через конфигурацию;
- Отключённый/упавший источник не прерывает сбор остальных;
- `status` показывает health по каждому источнику.

**Обязательные тесты:** изоляция ошибок источника, переключение enabled/disabled, парсинг каждого нового типа источника на фикстурах.

**Проверка результата:** прогон pipeline по всем источникам с симуляцией сбоя одного из них.

**Условие перехода к M7:** критерии выполнены.

## M7 — Hardening

**Цель:** эксплуатационная надёжность.

**Входит:**
- Recovery после ошибок (повторная обработка `error`/незавершённых статей)
- Backup данных SQLite
- Rate limits (источники, LM Studio, Telegram API)
- Source health и monitoring (логи, простые метрики прогонов)
- Диагностические CLI-команды (`doctor`: проверка доступности LM Studio, Telegram, источников, БД)
- Эксплуатационная документация

**Явно НЕ входит:** мониторинговые системы (Grafana и т.п.), alerting как отдельный сервис.

**Ожидаемые файлы:** `cli doctor`, скрипт backup, раздел эксплуатации в README/документации.

**Зависимости:** M6.

**Критерии готовности:**
- После принудительного сбоя (kill во время прогона) следующий запуск восстанавливается без дублей и потерь;
- Backup создаётся и восстанавливается;
- `doctor` диагностирует все внешние зависимости.

**Обязательные тесты:** восстановление после прерывания, backup/restore.

**Проверка результата:** сценарии сбоя + восстановление.

## MVP Definition

MVP считается работающим, когда система **автоматически** проходит полный сценарий для новостей SMS/messaging-экосистемы:

1. Получить реальные новости из источников;
2. Сохранить их в SQLite;
3. Удалить/не обработать дубликаты (повторный запуск не обрабатывает повторно);
4. Определить релевантность SMS/messaging-тематике (общие телеком-новости отфильтрованы);
5. Классифицировать тип новости;
6. Обработать выбранные новости локальной LLM (LM Studio): саммари, перевод при необходимости;
7. Сформировать публикацию и отправить её в тестовый/рабочий Telegram-канал;
8. **Повторный запуск не приводит к повторной публикации** уже обработанной новости.

### Конкретные проверяемые критерии MVP

| # | Критерий | Как проверить |
|---|---|---|
| 1 | Полный прогон `python -m telecom_news run` завершается с exit code 0 | запуск CLI |
| 2 | В БД появились статьи из реальных источников со статусами, отражающими обработку | запрос к SQLite / CLI `status` |
| 3 | Дубликаты не сохраняются повторно | два запуска `collect`, сравнение строк по hash/URL |
| 4 | Нерелевантные (общие телеком) статьи помечены `skipped` и не опубликованы | проверка `relevance`/статусов в БД |
| 5 | Релевантные SMS-статьи имеют `category`, саммари на целевом языке, статус `processed` | содержимое `llm_result` в БД |
| 6 | В Telegram-канале появилось корректно отформатированное сообщение с ссылкой на новость | визуальная проверка канала |
| 7 | Повторный запуск `run` не публикует уже опубликованные статьи повторно (статус `published`) | повторный запуск + проверка канала и БД |
| 8 | Недоступность LM Studio не роняет pipeline; статьи обрабатываются при следующем запуске | остановка LM Studio, прогон, перезапуск |

MVP = M0…M4 (ручной/полуручной сценарий) + критерии выше. M5 делает сценарий полностью автоматическим и входит в целевой MVP-pipeline («автоматизированная система ежедневного мониторинга»).

## Non-goals for MVP

Отложены, не входят в обязательный путь к MVP без конкретного обоснования:

| Non-goal | Статус / когда рассматривать |
|---|---|
| FastAPI / HTTP API | deferred (D-004) — только при подтверждённом use case |
| Web UI | после MVP, при необходимости |
| PostgreSQL | storage абстрагирует драйвер; при росте данных/конкурентности |
| Redis / очереди | вместе с distributed workers |
| Docker/Kubernetes | при деплое на сервер |
| Distributed workers | при превышении производительности одного процесса |
| Сложная семантическая дедупликация (embeddings) | после MVP, если межисточниковые дубли станут проблемой |
| Scraping сайтов, для которых достаточно RSS/API | только там, где надёжного интерфейса нет (M6) |
| Аналитика Telegram-канала | после MVP |
| Пользовательские аккаунты и authentication | вместе с FastAPI, если появится |

## Статусы решений DECISIONS.md по итогам planning

- **D-007 (предпочтение структурированному официальному интерфейсу; RSS или API):** статус `proposed`. Первый реальный источник ещё не выбран и не проверен; конкретный механизм определяется в M1 после фактической проверки. RSS не объявляется обязательным до выбора источника.
- **D-008 (Telegram delivery):** статус **`accepted`** — публикация в Telegram является частью утверждённой цели проекта и MVP Definition. Конкретная библиотека не фиксируется; реализация — M4.
