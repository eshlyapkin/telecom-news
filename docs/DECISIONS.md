# DECISIONS — telecom-news

Журнал технических решений. Формат записи: решение, статус (proposed / accepted / superseded), причина, последствия.

---

## D-001: Язык и экосистема

- **Решение:** Проект на Python 3.10+, структура `src/` layout.
- **Статус:** accepted
- **Причина:** Указано в README как требование; src-layout — стандарт для пакетов с pip install -e.
- **Последствия:** Нужен pyproject.toml (ещё не создан).

## D-002: Архитектура по слоям

- **Решение:** Три основных слоя: Collectors → Processors → Storage. HTTP API Layer не входит в MVP (см. D-004).
- **Статус:** accepted
- **Причина:** Позволяет независимо развивать сбор, обработку и хранение.
- **Последствия:** Каждый слой — отдельный пакет внутри `src/telecom_news/`.

## D-003: Базовая СУБД — SQLite

- **Решение:** По умолчанию SQLite, с возможностью переключения на PostgreSQL.
- **Статус:** accepted
- **Причина:** Указано в README; нулевая конфигурация для локальной разработки.
- **Последствия:** Слой storage должен абстрагировать драйвер БД (ещё не реализован).

## D-004: Интерфейс — CLI для MVP; FastAPI отложен

- **Решение:** Для текущего MVP обязательным интерфейсом является только CLI (`python -m telecom_news`) как простой интерфейс для ручного запуска pipeline, отладки, dry-run и служебных команд. REST API на FastAPI **не входит в обязательный MVP**.
- **Статус:** deferred (FastAPI) / accepted (CLI)
- **Причина:** Целевая система на MVP — фоновый pipeline: источники → сбор → нормализация → хранение и дедупликация → обработка локальной LLM через LM Studio → подготовка публикации → Telegram. HTTP API для этого сценария не требуется.
- **Последствия:**
  - FastAPI добавляется **только при появлении подтверждённого use case** для HTTP API (статус `proposed` до того момента).
  - Зависимости fastapi/uvicorn в pyproject.toml пока **не фиксируются**.
  - Каталог `src/telecom_news/api/` не является обязательным для MVP; создаётся только при подтверждении FastAPI.

## D-005: Система постоянной памяти проекта

- **Решение:** Ввести каталог `docs/` с файлами PROJECT_STATE.md, DECISIONS.md, SESSION_HANDOFF.md, AI_WORKFLOW.md как источник истины для LLM между сессиями.
- **Статус:** accepted
- **Причина:** Позволяет новому чату восстановить состояние без доступа к предыдущему разговору.
- **Последствия:** Обязательное обновление этих файлов в конце каждой сессии (см. AI_WORKFLOW.md).

## D-006: Git — ветка master, коммиты только по разрешению

- **Решение:** Инициализация на ветке `master`; не создавать commit без явного разрешения пользователя.
- **Статус:** accepted
- **Причина:** git init выбрал master по умолчанию; правило о коммитах задано пользователем.
- **Последствия:** Первый коммит пока не сделан.

## D-007: Первый источник — Sinch Blog по RSS

- **Решение:** Первый реальный источник — блог Sinch (customer communications), RSS `https://sinch.com/blog/feed/` (id `sinch-blog`, язык en). Механизм — RSS через `httpx` + `feedparser` (`collectors/rss.py`); scraping не используется.
- **Статус:** accepted (M1)
- **Причина:** Источник проверен фактически: фид отдаёт HTTP 200 `application/rss+xml`, свежие EN-материалы о business messaging/CPaaS (RCS, SMS-платформа Engage), регулярность ~2–3 поста в неделю, работает с небраузерным User-Agent. Отклонены: MEF (лучший доменный фит, но RSS отдаёт Cloudflare-403 небраузерным клиентам — нельзя верифицировать и полагаться в M1), Capacity (общий telecom без SMS-фокуса в свежих материалах), Twilio Blog (общий dev-блог, шум), Sinch newsroom (редкие PR, последний — 3 мес. назад), Telesign/TheFastMode/Plivo/Infobip/Bandwidth (пустой или отсутствующий RSS).
- **Последствия:** M1 реализован на RSS-коллекторе; следующие источники добавляются в M6; MEF можно пересмотреть в M6 при появлении надёжного способа доступа.

## D-008: Telegram как канал доставки

- **Решение:** Публикация подготовленных SMS/messaging-новостей в Telegram-канале через Bot API.
- **Статус:** accepted
- **Причина:** Публикация в Telegram является частью утверждённой цели проекта и MVP Definition (см. ARCHITECTURE.md §1, ROADMAP.md «MVP Definition»). Конкретная Telegram-библиотека на этом этапе не фиксируется — фактическая реализация остаётся M4.
- **Последствия:** Отдельный модуль доставки `delivery/telegram.py` (см. ARCHITECTURE.md §3.10); реализация выполнена в M4.

## D-009: Telegram Bot API через httpx и HTML

- **Решение:** Использовать прямой Telegram Bot API через существующий `httpx`; формат сообщений — HTML с экранированием пользовательского текста.
- **Статус:** accepted
- **Причина:** Не добавляет runtime-зависимость и поддерживает `sendMessage`, `retry_after`, dry-run и контролируемые mock-тесты.
- **Последствия:** Токен и chat ID передаются только через `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`; ошибки отправки не меняют статус `processed`, а успешная отправка атомарно переводит статью в `published`.

## D-010: Официальные RSS-источники для M6

- **Решение:** Добавить к Sinch Blog официальные RSS-ленты Twilio Blog, Infobip Blog и GSMA Newsroom.
- **Статус:** accepted
- **Причина:** Все четыре endpoint были фактически проверены как доступные RSS/XML-источники; Twilio и Infobip покрывают CPaaS/business messaging, GSMA добавляет отраслевые и регуляторные новости. LLM-фильтр сохраняет только материалы, релевантные SMS/messaging.
- **Последствия:** `run` собирает все enabled-источники; ошибка одного источника изолируется, а последняя проверка и ошибка сохраняются в `source_health`. Источники остаются конфигурационными и могут отключаться без изменения кода.

## D-011: Русскоязычные источники и кириллический сигнал релевантности

- **Решение:** (1) Расширен реестр источников: добавлено 12 русскоязычных лент — CNews (`telecom`, `safe`, `biz`, `internet`, `corp`), SecurityLab (`news`, `analytics`, `vulnerabilities`), Anti-Malware.ru (`news`, `analytics`, `press`), NAG (`all`). Восемь включены по умолчанию, четыре объявлены с `enabled=False` (низкий сигнальный шум: корпоративные внедрения, поток CVE, пресс-релизы, NAG). Итого: 19 объявленных источников, 15 активных. (2) `MESSAGING_TERMS` в `processors/relevance.py` дополнен кириллическими написаниями (`смс`, `эсэмэс`, `смшинг`, `а2п`, `мессендж`, `чат-бот`, `телеграм`, `код подтверждения`, `одноразовый пароль`, `ммс`, `вотсап`) и `telegram`/`chatbot` для латиницы. (3) Исправлен мёртвый guard: `is_obviously_off_topic()` получил правило по заголовку, иначе он не мог сработать из `check_relevance()`.
- **Статус:** accepted (код и тесты проверены; «user verified» фиды требуют живого прогона — см. ниже)
- **Причина:** После добавления RU-источников в M7 в канал перестало поступать что-либо. Deterministic guard M6 (`9a7c3a6`) требовал вхождения SMS-термина из списка, состоявшего **только из латинских** строк; русские тексты пишут «СМС», «чат-бот», «мессенджер», поэтому `check_relevance()` возвращал `relevant=False` **до обращения к LLM**, и все RU-статьи уходили в `skipped`. Английские ленты (Sinch/Twilio/Infobip/GSMA) публикуют 2–3 раза в неделю, поэтому пустого канала это не компенсировало.
- **Проверка endpoint'ов:** `cnews-telecom`, `cnews-safe`, `anti-malware-news` проверены агентом 2026-09-11 (фид отвечает, видны записи за 2026-09-11). Остальные девять приняты по проверке пользователя: песочница агента не имеет исходящей сети, повторная проверка невозможна — **NOT VERIFIED агентом**. `nag.ru/rss/all` отвечает, но отдаёт `text/html`; `parse_feed()` принимает байты без проверки MIME (тест `test_collector_ignores_content_type_of_the_response`), однако непустота записей не подтверждена → источник объявлен выключенным.
- **Последствия:** Отслеживающие параметры (`utm_source`) в конфигурацию не попадают — есть тест. Включение отключённого источника требует правки `enabled` в `config.py` (`collect` по выключенному источнику завершается с кодом 2). Расширение списка терминов — это компромисс в пользу полноты: часть нерелевантных материалов теперь доходит до LLM и отсекается там. Сознательно не добавлены в сигнал `сообщени` («по сообщению пресс-службы»), `рассылк` (почтовый шум), `верификац` (KYC/финтех), `ркс` (столкновение с «РКС»).

## D-012: Узкие источники передают релевантность LLM (bypass детерминированного guard)

- **Решение:** `SourceConfig.relevance_gate` (`"strict"` по умолчанию, `"llm"` для узких лент). При `"llm"` `check_relevance(client, article, use_gate=False)` пропускает keywords-guard и сразу спрашивает модель. Переведены: `content-review`, `anti-malware-news`, `anti-malware-analytics`, `securitylab-news`, `securitylab-analytics`. Широкие ленты (Sinch/Twilio/Infobip/GSMA/CNews/Хабр/ИКС) остаются на `strict`.
- **Статус:** accepted (решение пользователя от 2026-09-11: «и то, и другое» — расширить источники и ослабить фильтр).
- **Причина:** Замер D-011 показал, что у `CNews /news/line/` нет описания в фиде, а у узких RU-лент SMS-сюжет часто виден только внутри статьи. Guard читает только заголовок и текст фида, поэтому такие материалы уходили в `skipped` без вызова модели — именно это давало «пустой канал». Цена решения: каждый материал таких лент теперь стоит один LLM-вызов.
- **Последствия:** Ключевой список остаётся экономичным фильтром для широких лент; для узких он больше не теряет статьи. Проверено тестом `test_gate_bypass_sends_articles_without_keywords_to_the_model` и тестом конфигурации (`relevance_gate` по источникам).

## D-013: Языки публикации и подписки пользователей

- **Решение:** (1) Публикация ведётся на наборе языков `TELECOM_NEWS_TARGET_LANGS` (по умолчанию `ru`; старый `TELECOM_NEWS_TARGET_LANG` продолжает работать). На каждый язык — своё сообщение. (2) Каналы: `TELEGRAM_CHAT_ID` (первый язык) и/или `TELEGRAM_CHAT_ID_<LANG>` для остальных. (3) Подписки в личке бота: `/start` → клавиатура выбора языков (✅/⬜), `/language` меняет набор в любой момент, `/status`, `/stop`, `/help`. (4) Контент на язык хранится в таблице `renditions` и генерируется лениво (`ensure_rendition`): языки каналов — на этапе `process`, языки подписчиков — при первой доставке. (5) Идемпотентность и аудит — таблица `deliveries` с ключом `(chat_id, article_id, lang)`; `publish` и `deliver` не отправляют одно и то же дважды. (6) Окно свежести `SUBSCRIBER_MAX_AGE_HOURS` (24), лимит `SUBSCRIBER_MAX_PER_CYCLE` (10) сообщений на подписчика за цикл, не более `SUBSCRIBER_MAX_ATTEMPTS` (3) попыток на сообщение, при `403` подписчик помечается `blocked`.
- **Статус:** accepted (решения пользователя 2026-09-11: гибрид «канал + личка», отдельные сообщения на каждый язык, ленивый кэшируемый перевод).
- **Причина:** Требование «при подключении выбрать язык, менять в любой момент и получать несколько языков одновременно» нельзя выполнить в одном канале: выбор языка — состояние пользователя. Каналы не ломаются: они остаются отдельным, независимым способом доставки.
- **Последствия:** Новые таблицы `renditions`, `subscribers`, `subscriber_languages`, `deliveries`, `bot_state` (аддитивная миграция, `CREATE TABLE IF NOT EXISTS`). `publish` больше не вызывает LLM: он публикует готовые рендеры и для строк, созданных до M8, использует `llm_result.summary`. Команды процессов: `bot` (долгоживущий long-polling, `--once` для шедулера) и `deliver` (рассылка подписчикам). Обработка команд реализована в `bot.py` (`handle_update` — чистая логика + список действий), тестируется без сети. Открытые вопросы дизайна закрыты, документ `docs/DESIGN_LANGUAGE_SUBSCRIPTIONS.md` переведён в статус implemented.

## D-014: Два messaging-фокусированных англоязычных источника

- **Решение:** Добавлены `mef-news` (`https://mobileecosystemforum.com/feed/`) и `mobilesquared` (`https://www.mobilesquared.co.uk/feed/`), оба `en`, `relevance_gate="strict"`. Итого 21 объявленный источник, 17 включённых.
- **Статус:** accepted (решение пользователя «расширять источники и ослабить фильтр», см. D-012).
- **Причина:** Симптом «в канале тихо» частично объясняется нехваткой материала, а не только фильтром: 2026-09-11 в CNews/Content-Review/Anti-Malware не было ни одной SMS/messaging-статьи. MEF публикует недельные дайджесты мобильной отрасли (в выпуске от 2026-09-11 — Jio RBM для iPhone, то есть A2P/RCS), Mobilesquared пишет только про A2P SMS, RCS и WhatsApp Business.
- **Проверка:** оба endpoint'а отвечают и отдают свежие записи; проверено агентом 2026-09-11 **внешним загрузчиком страниц**, потому что песочница агента не имеет исходящей сети. Живой `collect` на машине пользователя — NOT VERIFIED.
- **Последствия:** MEF-дайджест проходит keyword-guard (RCS/A2P/OTP присутствуют в тексте), поэтому расход LLM остаётся ограниченным. Кандидаты, которые не добавлены: `telemediamagazine.com` (телепатии/платежи, DCB — смежная тема, много шума), `the-mobile-network.com` и `telecoms.com` (5G/RAN, SMS почти нет).

## D-015: Ограниченные ретраи статей (исправление вечной блокировки очереди)

- **Решение:** (1) В `articles` добавлена колонка `attempts` (аддитивная миграция через `PRAGMA table_info` + `ALTER TABLE`), инкремент — `Database.mark_error()`. (2) `Database.reset_errors(limit, max_attempts=3)` возвращает в `new` только статьи с `attempts < max_attempts`; `max_attempts=None` — принудительный полный сброс. (3) CLI `recover --max-attempts N` (по умолчанию 3, `0` = сбросить всё), `run` вызывает `recover` с лимитом 3. (4) `diagnose` показывает `parked_errors` и подсказывает `recover --max-attempts 0`. (5) Все места, где статья уходила в `error`, теперь считают попытки (`process`: плохой ответ релевантности, пустой рендер; `publish`: отсутствующий рендер).
- **Статус:** accepted (пользователь: «почини эту ошибку»).
- **Причина:** `run` перед каждым прогоном вызывал `recover`, который возвращал **все** `error`-статьи в `new` без ограничений, а `process` берёт самые старые `new` с лимитом `--limit` (в `run_pipeline.sh` — 10). Статьи с постоянно невалидным ответом LLM (или с отсутствующим рендером) сортировались первыми, каждый прогон заново занимали весь бюджет обработки и снова падали в `error`. Новые статьи до модели не доходили — канал молчал бесконечно, а `status` показывал растущий `error`.
- **Проверка:** регрессионный тест `test_repeatedly_broken_article_does_not_starve_the_queue` (3 «отравленные» статьи + 1 свежая; после 4 прогонов свежая — `processed`, три остаются `error`), тесты хранилища на счётчик попыток, границы сброса и миграцию старой БД без колонки `attempts`, тест `diagnose` на «запаркованные» ошибки.
- **Последствия:** статья, которую модель не может обработать, остаётся в `error` и больше не блокирует очередь; вернуть её в работу можно вручную (`recover --max-attempts 0`) или подняв лимит. Старые БД мигрируются автоматически при первом обращении.

## D-016: Каталог источников и импорт из исследовательской таблицы

- **Решение:** (1) `sources_catalog.py` — каталог эндпоинтов с полями `id`, `url`, `kind` (`news`/`status`), `language`, `grade` (`A+`/`A`), `topic`, `gate`, `enabled`, `verified`, `note`. (2) В `config.SOURCES` попадают только `kind="news"`; каталог мержится с курируемыми записями, совпадение `id` — ошибка конфигурации. (3) `kind="status"` (JSON-эндпоинты статус-страниц, `*.statuspage.io`, `/history.rss`) объявлены, но не собираются: `feedparser` их не разбирает, а содержимое — «все системы работают»/инциденты, а не новости. Это материал для будущего мониторинга доступности. (4) `python -m telecom_news sources [--kind news|status|all] [--json] [--verify]` — список каталога, проверка целостности (`catalog_issues`) и опциональная живая проверка каждого включённого news-источника. (5) `python -m telecom_news sources import --csv <файл> [--dry-run]` — импорт таблицы: колонки распознаются по русским и английским заголовкам, строки с «исключён / 404 / 410 / 403 / 502 / timeout» отбрасываются, уже объявленные в `config.SOURCES` URL пропускаются (курируемая запись главнее), `id` — транслитерированный слаг издателя с разрешением коллизий. Вид источника определяется типом и URL, **не** MIME (см. ниже). (6) Импортёр пишет готовый модуль `sources_catalog.py`; поддержка XLSX — через опциональный `openpyxl` (основной путь — экспорт в CSV).
- **Статус:** accepted (пользователь предоставил таблицу 100 источников + 17 дополнительных).
- **Причина:** реестр из 100+ источников нельзя поддерживать вручную в `config.py`; при этом часть таблицы — статус-страницы, которые не являются новостями и сломали бы `collect` (JSON вместо RSS). Импорт из таблицы делает её источником истины, а `sources --verify` проверяет эндпоинты на машине пользователя (у агента нет исходящей сети).
- **Проверка:** `tests/test_source_import.py` (17 тестов) — заголовки таблицы, классификация kind, транслитерация, пропуск исключённых и курируемых строк, разрешение коллизий, чтение semicolon-CSV с BOM, что сгенерированный модуль импортируется и проходит `catalog_issues()`; проверка целостности самого каталога; тесты CLI `sources`, `sources --verify` (мок сети), `sources import`.
- **Импорт выполнен 2026-09-11** из `docs/sms_messaging_rss_100_unique_sources_verified_2026-09-11.xlsx` (6 листов, 189 строк данных на 4 листах): в каталоге **102 записи — 42 новостные ленты и 60 status-эндпоинтов**; реестр `config.SOURCES` — 63 источника, 59 включённых. Разбор по листам: «100 уникальных» — 100 строк, «A+ приоритет» — 57 (дубли основного списка по URL, отброшены), «Доп. тематические» — 17, «Не включено» — 15 (отброшены по статусу таблицы: «не вошёл в строгие 100», «не подтверждён / не работает» — 404/403/410/502/timeout/HTML); «Сводка» и «Методология» распознаны как не-данные и пропущены. Итог разбора 189 строк: 102 записи, 87 пропусков — 54 дубля endpoint (лист «A+ приоритет» почти целиком повторяет «100 уникальных»), 18 совпадений с рукописными записями `config.py` (CNews, SecurityLab, Anti-Malware, Habr, Sinch, Twilio, Infobip, GSMA, Content-Review, IKS, NAG, MEF, MobileSquared), 15 строк, отклонённых самой таблицей.
- **MIME не является решающим признаком:** 60 status-эндпоинтов в таблице помечены как `application/rss+xml`, поэтому вид источника определяется колонкой «Тип источника» (`Operational status / incidents`), URL (`status.<host>/history.rss`, `*.statuspage.io`) и JSON-форматом. Без этого правила 60 лент инцидентов были бы включены как новостные и засорили бы `collect`. Есть регрессионный тест.
- **Рукописные записи переживают импорт:** `mef-news` и `mobilesquared` объявлены в `config.py`, а не в каталоге, поэтому массовый импорт их не удаляет (их строки из таблицы пропускаются как «curated entry wins»). Повторный импорт идемпотентен: записи, пришедшие из каталога, не исключают сами себя (регрессионный тест `test_import_does_not_exclude_entries_that_came_from_the_catalog`).
- **Заголовки листов сопоставляются по отдельности:** у «100 уникальных» колонка называется «RSS / Atom endpoint», у «Не включено» — «Endpoint». Общий mapping по первой строке книги молча терял endpoint у отклонённых строк, и они выглядели как «пустые», а не как исключённые самой таблицей. Теперь mapping строится на каждый лист (`test_parse_rows_maps_headers_per_sheet`), и CLI печатает честные причины пропусков.
- **Порядок для пользователя:** `sources import --csv <файл> --dry-run` → `sources import` → `sources --kind all` → `sources --verify` → `git diff`.
