# DECISIONS — telecom-news

Журнал технических решений. Формат записи: решение, статус (proposed / accepted / superseded), причина, последствия.

---

## D-001: Язык и экосистема

- **Решение:** Проект на Python 3.10+, структура `src/` layout.
- **Статус:** accepted
- **Причина:** Указано в README как требование; src-layout — стандарт для пакетов с pip install -e.
- **Последствия:** Нужен pyproject.toml (ещё не создан).

## D-002: Архитектура по слоям

- **Решение:** Три основных слоя: Collectors → Processors → Storage. HTTP API Layer не входит в MVP (см. D-004).
- **Статус:** accepted
- **Причина:** Позволяет независимо развивать сбор, обработку и хранение.
- **Последствия:** Каждый слой — отдельный пакет внутри `src/telecom_news/`.

## D-003: Базовая СУБД — SQLite

- **Решение:** По умолчанию SQLite, с возможностью переключения на PostgreSQL.
- **Статус:** accepted
- **Причина:** Указано в README; нулевая конфигурация для локальной разработки.
- **Последствия:** Слой storage должен абстрагировать драйвер БД (ещё не реализован).

## D-004: Интерфейс — CLI для MVP; FastAPI отложен

- **Решение:** Для текущего MVP обязательным интерфейсом является только CLI (`python -m telecom_news`) как простой интерфейс для ручного запуска pipeline, отладки, dry-run и служебных команд. REST API на FastAPI **не входит в обязательный MVP**.
- **Статус:** deferred (FastAPI) / accepted (CLI)
- **Причина:** Целевая система на MVP — фоновый pipeline: источники → сбор → нормализация → хранение и дедупликация → обработка локальной LLM через LM Studio → подготовка публикации → Telegram. HTTP API для этого сценария не требуется.
- **Последствия:**
  - FastAPI добавляется **только при появлении подтверждённого use case** для HTTP API (статус `proposed` до того момента).
  - Зависимости fastapi/uvicorn в pyproject.toml пока **не фиксируются**.
  - Каталог `src/telecom_news/api/` не является обязательным для MVP; создаётся только при подтверждении FastAPI.

## D-005: Система постоянной памяти проекта

- **Решение:** Ввести каталог `docs/` с файлами PROJECT_STATE.md, DECISIONS.md, SESSION_HANDOFF.md, AI_WORKFLOW.md как источник истины для LLM между сессиями.
- **Статус:** accepted
- **Причина:** Позволяет новому чату восстановить состояние без доступа к предыдущему разговору.
- **Последствия:** Обязательное обновление этих файлов в конце каждой сессии (см. AI_WORKFLOW.md).

## D-006: Git — ветка master, коммиты только по разрешению

- **Решение:** Инициализация на ветке `master`; не создавать commit без явного разрешения пользователя.
- **Статус:** accepted
- **Причина:** git init выбрал master по умолчанию; правило о коммитах задано пользователем.
- **Последствия:** Первый коммит пока не сделан.

## D-007: Первый источник — Sinch Blog по RSS

- **Решение:** Первый реальный источник — блог Sinch (customer communications), RSS `https://sinch.com/blog/feed/` (id `sinch-blog`, язык en). Механизм — RSS через `httpx` + `feedparser` (`collectors/rss.py`); scraping не используется.
- **Статус:** accepted (M1)
- **Причина:** Источник проверен фактически: фид отдаёт HTTP 200 `application/rss+xml`, свежие EN-материалы о business messaging/CPaaS (RCS, SMS-платформа Engage), регулярность ~2–3 поста в неделю, работает с небраузерным User-Agent. Отклонены: MEF (лучший доменный фит, но RSS отдаёт Cloudflare-403 небраузерным клиентам — нельзя верифицировать и полагаться в M1), Capacity (общий telecom без SMS-фокуса в свежих материалах), Twilio Blog (общий dev-блог, шум), Sinch newsroom (редкие PR, последний — 3 мес. назад), Telesign/TheFastMode/Plivo/Infobip/Bandwidth (пустой или отсутствующий RSS).
- **Последствия:** M1 реализован на RSS-коллекторе; следующие источники добавляются в M6; MEF можно пересмотреть в M6 при появлении надёжного способа доступа.

## D-008: Telegram как канал доставки

- **Решение:** Публикация подготовленных SMS/messaging-новостей в Telegram-канале через Bot API.
- **Статус:** accepted
- **Причина:** Публикация в Telegram является частью утверждённой цели проекта и MVP Definition (см. ARCHITECTURE.md §1, ROADMAP.md «MVP Definition»). Конкретная Telegram-библиотека на этом этапе не фиксируется — фактическая реализация остаётся M4.
- **Последствия:** Отдельный модуль доставки `delivery/telegram.py` (см. ARCHITECTURE.md §3.10); реализация выполнена в M4.

## D-009: Telegram Bot API через httpx и HTML

- **Решение:** Использовать прямой Telegram Bot API через существующий `httpx`; формат сообщений — HTML с экранированием пользовательского текста.
- **Статус:** accepted
- **Причина:** Не добавляет runtime-зависимость и поддерживает `sendMessage`, `retry_after`, dry-run и контролируемые mock-тесты.
- **Последствия:** Токен и chat ID передаются только через `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`; ошибки отправки не меняют статус `processed`, а успешная отправка атомарно переводит статью в `published`.

## D-010: Официальные RSS-источники для M6

- **Решение:** Добавить к Sinch Blog официальные RSS-ленты Twilio Blog, Infobip Blog и GSMA Newsroom.
- **Статус:** accepted
- **Причина:** Все четыре endpoint были фактически проверены как доступные RSS/XML-источники; Twilio и Infobip покрывают CPaaS/business messaging, GSMA добавляет отраслевые и регуляторные новости. LLM-фильтр сохраняет только материалы, релевантные SMS/messaging.
- **Последствия:** `run` собирает все enabled-источники; ошибка одного источника изолируется, а последняя проверка и ошибка сохраняются в `source_health`. Источники остаются конфигурационными и могут отключаться без изменения кода.

## D-011: Русскоязычные источники и кириллический сигнал релевантности

- **Решение:** (1) Расширен реестр источников: добавлено 12 русскоязычных лент — CNews (`telecom`, `safe`, `biz`, `internet`, `corp`), SecurityLab (`news`, `analytics`, `vulnerabilities`), Anti-Malware.ru (`news`, `analytics`, `press`), NAG (`all`). Восемь включены по умолчанию, четыре объявлены с `enabled=False` (низкий сигнальный шум: корпоративные внедрения, поток CVE, пресс-релизы, NAG). Итого: 19 объявленных источников, 15 активных. (2) `MESSAGING_TERMS` в `processors/relevance.py` дополнен кириллическими написаниями (`смс`, `эсэмэс`, `смшинг`, `а2п`, `мессендж`, `чат-бот`, `телеграм`, `код подтверждения`, `одноразовый пароль`, `ммс`, `вотсап`) и `telegram`/`chatbot` для латиницы. (3) Исправлен мёртвый guard: `is_obviously_off_topic()` получил правило по заголовку, иначе он не мог сработать из `check_relevance()`.
- **Статус:** accepted (код и тесты проверены; «user verified» фиды требуют живого прогона — см. ниже)
- **Причина:** После добавления RU-источников в M7 в канал перестало поступать что-либо. Deterministic guard M6 (`9a7c3a6`) требовал вхождения SMS-термина из списка, состоявшего **только из латинских** строк; русские тексты пишут «СМС», «чат-бот», «мессенджер», поэтому `check_relevance()` возвращал `relevant=False` **до обращения к LLM**, и все RU-статьи уходили в `skipped`. Английские ленты (Sinch/Twilio/Infobip/GSMA) публикуют 2–3 раза в неделю, поэтому пустого канала это не компенсировало.
- **Проверка endpoint'ов:** `cnews-telecom`, `cnews-safe`, `anti-malware-news` проверены агентом 2026-09-11 (фид отвечает, видны записи за 2026-09-11). Остальные девять приняты по проверке пользователя: песочница агента не имеет исходящей сети, повторная проверка невозможна — **NOT VERIFIED агентом**. `nag.ru/rss/all` отвечает, но отдаёт `text/html`; `parse_feed()` принимает байты без проверки MIME (тест `test_collector_ignores_content_type_of_the_response`), однако непустота записей не подтверждена → источник объявлен выключенным.
- **Последствия:** Отслеживающие параметры (`utm_source`) в конфигурацию не попадают — есть тест. Включение отключённого источника требует правки `enabled` в `config.py` (`collect` по выключенному источнику завершается с кодом 2). Расширение списка терминов — это компромисс в пользу полноты: часть нерелевантных материалов теперь доходит до LLM и отсекается там. Сознательно не добавлены в сигнал `сообщени` («по сообщению пресс-службы»), `рассылк` (почтовый шум), `верификац` (KYC/финтех), `ркс` (столкновение с «РКС»).
